# PF004  NVIC / interrupt priority conflict

## What goes wrong
Cortex-M priority registers reset to 0, which is the HIGHEST urgency. An
interrupt that is enabled but never given a priority therefore preempts
almost everything, including the SysTick that HAL_Delay() depends on
(HAL sets SysTick to a low urgency by default).

Priorities also have limited width: STM32 Cortex-M3/M4/M7 parts implement 4
bits (M0/M0+ parts 2). NVIC_PRIORITYGROUP_x splits those bits into a preempt
part and a sub part; for example GROUP_2 leaves preempt 0..3 and sub 0..3.
HAL_NVIC_SetPriority masks a too-large value to the available bits, so
preempt 5 in GROUP_2 silently becomes 1.

Equal preempt priority means neither interrupt can preempt the other; the
tie is broken by sub-priority, then IRQ number.

Finally, HAL_Delay() spins on a counter that only SysTick_Handler advances.
If SysTick is not the least urgent interrupt, an ISR of equal or higher
urgency that calls HAL_Delay() hangs forever.

## Example
    HAL_NVIC_EnableIRQ(TIM2_IRQn);      /* no HAL_NVIC_SetPriority: runs at 0 */

    NVIC.PriorityGroup=NVIC_PRIORITYGROUP_2
    NVIC.USART2_IRQn=true:5:0:...       /* preempt 5, but only 0..3 exist */

## How to fix
Give every enabled interrupt an explicit priority within the range of the
configured group, keep SysTick numerically largest (least urgent), and use
distinct priorities where ordering between interrupts matters.

## What Preflight checks (select with --nvic-checks a,b1,b2,b3)
- a  enabled IRQ with no SetPriority (.c), or unreadable priority (.ioc)
- b1 priority out of range for the group                        -> error
- b2 two enabled IRQs tied at a deliberately set, non-zero priority
                                                                -> warning
- b3 SysTick is not the least-urgent enabled interrupt          -> warning
