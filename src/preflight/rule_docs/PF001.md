# PF001  Pin conflict

## What goes wrong
Every GPIO pad reaches the chip's peripherals through an alternate-function
(AF) multiplexer. The mux has one select field per pin (GPIOx_AFRL/AFRH on
STM32), so a pin routes exactly ONE peripheral signal at a time.

If two signals are assigned to one pin, both peripheral inits run and the
last write to the mux wins. The loser is configured, clocked and "running",
but its signal never reaches the pad. There is no fault and no HAL error:
a UART just stays silent, or a PWM output never toggles.

CubeMX's pin view prevents this, so it usually comes from hand-edited or
merged .ioc files, or from two MspInit functions in C that each configure
the same pin.

## Example
.ioc (same key twice, or two aliases of one pad):

    PA2.Signal=USART2_TX
    PA2.Signal=S_TIM2_CH3

C (two MspInit functions, same pin, different alternates):

    HAL_UART_MspInit:     Pin = GPIO_PIN_2;  Alternate = GPIO_AF7_USART2;
    HAL_TIM_MspPostInit:  Pin = GPIO_PIN_2;  Alternate = GPIO_AF1_TIM2;

## How to fix
Decide which peripheral owns the pin. Move the other signal to an alternate
pin the datasheet lists for it (CubeMX's Pinout view shows the options) and
delete the duplicate assignment.

## What Preflight checks
- One pin, different signals/alternates (duplicate key, alias such as
  PC14 vs PC14-OSC32_IN, or two C functions).       -> error
- One non-GPIO signal routed to two pins (.ioc).    -> error
- Pins configured but missing from Mcu.Pin*, or Mcu.PinsNb not matching the
  number of Mcu.PinN entries (.ioc).                -> warning

## Limits
No package pin-remap database: a few packages let two logical pin names share
one pad, which is not modelled.
