# PF003  Uninitialized peripheral use

## What goes wrong
A HAL handle (UART_HandleTypeDef huart2, SPI_HandleTypeDef hspi1, ...) is
only a struct. HAL_xxx_Init(&handle) does the real work: it calls
HAL_xxx_MspInit (enable the peripheral clock, configure the GPIO pins and
NVIC), programs the peripheral registers and moves the handle's state from
RESET to READY.

HAL_UART_Transmit, HAL_SPI_Transmit and friends check that state first. On
an uninitialised handle it is still RESET, so they return HAL_BUSY
immediately and nothing is sent. If the return value is ignored (very
common) there is no visible error. Even without the check, the peripheral
clock would be off, so register writes would have no effect.

## Example
    int main(void) {
      HAL_Init();
      MX_USART2_UART_Init();
      /* MX_SPI1_Init();  <- removed or forgotten */
      HAL_SPI_Transmit(&hspi1, buf, 4, 100);   /* returns HAL_BUSY */
    }

## How to fix
Call the peripheral's init (normally the CubeMX-generated MX_xxx_Init)
before the first use, and keep the generated call order. If you use
CubeMX's "generate peripheral init as a pair of .c/.h files", the init call
still belongs in main() before the use.

## What Preflight checks
Starting at main() (or every uncalled function if there is no main), it
follows calls into helper functions, so the usual MX_xxx_Init wrapper is
understood. A use with no init reachable before it is an error ("never
initialized" or "used before it is initialized"). A use inside an if/loop
block whose init exists elsewhere is downgraded to a warning.

## Limits
One file at a time: an init in another .c file looks like a missing init.
Control flow is treated as a straight line, and calls through function
pointers are not followed.
